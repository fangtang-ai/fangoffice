# B2 schema and local database review — 2026-10-16

## Local-only database acceptance

R2 now additionally permits the disposable native cluster under
`tmp/knowledge-pg-isolated`, bound only to `127.0.0.1:55432`. PostgreSQL 18.2,
pgvector 0.8.7, restricted roles and the 16-table candidate have been initialized
there with synthetic data only. All 15 tenant tables have real RLS/FORCE checks;
FK/CHECK/vector constraints and native backup/restore have been exercised.
No existing business database, cloud resource, Docker instance, billing,
deployment or push is involved. B4 queue and B6 claim/seal/publication slices
also pass locally; persistent B5 capacity, full B6 budget/metering atomicity and
B7 deletion/recovery remain unfinished. See ACCEPTANCE.md for the current mapping.

The source of the candidate is `src/schema/index.ts`, generated by the fixed
Drizzle ORM 0.45.2 / Kit 0.31.10 development dependencies. The three files under
`drizzle/` are generator output, not a migration handwritten from a design note.
Regenerate SQL, journal and snapshot together whenever an unmerged candidate
changes; do not edit just one of them or rewrite any applied migration history.
The accepted local artifact hashes are recorded in the ignored
`tmp/knowledge-pg-isolated/migration-receipt.json`. Future schema changes need
an explicit migration/reset plan; do not silently reapply over this local schema.

## Tables and relationships

| Group                       | Tables                                                                    |
| --------------------------- | ------------------------------------------------------------------------- |
| Control                     | `kb_index_profiles`, `kb_quotas`, `kb_spaces`                             |
| Lifecycle                   | `kb_documents`, `kb_operations`, `kb_versions`, `kb_builds`               |
| Derived content             | `kb_source_units`, `kb_chunks`, `kb_chunk_sources`, `kb_chunk_embeddings` |
| Reservations and evidence   | `kb_reservations`, `kb_evidence_manifests`, `kb_evidence_items`           |
| Metering and reconciliation | `kb_metering_events`, `kb_billing_receipts`                               |

- A verified subject is a non-null text `owner_id`, not a new UUID user or a
  cross-database FK to the website. Profiles are platform configuration without
  owner, credentials or private content. There is no knowledge-wallet balance.
- Composite owner/document/version/build keys bind each child to its real parent.
  Document active pointers include both version and build; desired pointers bind
  the operation and its target. Reservations bind the same document/base build.
  Metering binds the operation **and** its build, not two independently valid
  operations/builds of the same document and version.
- Initial/optional pointers use PostgreSQL's default MATCH SIMPLE, with explicit
  paired-NULL checks. Ingestion phases require a target version; deleted documents
  clear active/desired pointers. All FKs use NO ACTION, not bulk CASCADE or blanket
  DEFERRABLE. Cyclic tables are created before reverse FKs are added.
- Evidence items have a strong owner/manifest FK, but historical document/version/
  build/unit/profile IDs deliberately remain snapshots. They contain hashes,
  locators and code-point ranges, not retained excerpt text. Reading a snapshot
  still requires current authorization, tombstone, retention and hash checks.
- Bigint counters use exact BigInt values; SQL literal defaults avoid Kit's native
  BigInt JSON-serialization failure. Usage quantities use `numeric(38,0)` strings;
  token/byte observations remain bounded to int64. Unknown quantities are NULL,
  never invented zeroes. Capacity-change facts carry before/after bytes and an
  owner sequence; storage observations carry frozen window bounds/watermarks.
- Embeddings are a one-to-one, non-null `vector(1024)` thin table. This is only the
  local physical baseline, not proof of a deployed model's dimension. The local
  extension and dimension checks are verified separately. Chunks retain text/hash and `tsvector`; GIN
  supports lexical candidates, with no ANN index or global cross-owner dedup.
- Stable partial indexes cover one live ingestion per document, held reservations,
  pending delivery and receipt reconciliation. Other indexes support owner/build
  order and source mappings. No performance or query-plan measurements are claimed.

JSONB columns have schema-version and outer-shape checks. Existing bounded shared
contracts still validate detailed payloads before persistence; SQL checks alone
do not implement the semantic or size bounds of arbitrary nested JSON. The tables
do not make model/client-supplied snapshots trustworthy.

## Offline verification

The public test seams are Drizzle table configuration and generated SQL/snapshot/
journal files. They check 16-table membership, primary/unique/FK targets, owner and
parent columns, nullable-pointer combinations, source offsets, vector separation,
precision, metering subjects and receipt lifecycle shapes. Fresh generation in an
OS temporary directory must reproduce SQL and snapshot metadata (excluding the
random snapshot ID); both copies pass Kit check. A second normal generate must
report no schema change. No SQL is executed by these tests.

The schema export is intentionally not re-exported from the runtime package's
public entries. Service build input auditing and the repository-external runtime
installation smoke must remain green, with the existing deployment manifest/lock
unchanged. The candidate SQL is not copied into `dist/`. Only `db:apply:local`
explicitly applies it to the marked disposable cluster; startup never migrates.

## Required before execution or release

B3's offline candidate now declares ENABLE and owner policies for all 15 tenant
tables and keeps the SQL/snapshot/journal together. FORCE
is a separate `security/force-rls.sql` review supplement because the selected
ORM declaration does not snapshot it. Trusted runtime transactions and the
proposed role/gate/real-acceptance matrix are described in
[security/README.md](security/README.md). The explicit local entry now verifies
restricted grants, RLS, constraints and pool transactions; it does not implement
the full lifecycle or a production migration entry. The separate
`security/immutable-facts.sql` supplement now protects four tables' facts, without
changing generated artifacts or runtime grants; its explicit local-only entry
checks the accepted baseline and records an independent hash receipt.
The subsequent `security/build-content.sql` supplement freezes Build identity and
sealed snapshots and gates append-only content through a building/live parent
FOR SHARE lock. It chains the previous receipt without rewriting generated SQL.
Actual sealing validation, generation/queue-attempt admission, quota, publication
and authorized GC remain separate prerequisites, not new runtime privileges.

1. Confirm an isolated database, migration role, server/extension versions and the
   actual model dimension. Provisioning `vector` is separate: the candidate does
   not CREATE EXTENSION, roles, pg-boss tables or a website schema.
2. Review/apply B3 owner policies, FORCE RLS, minimum role grants and trusted
   transaction-local identity, then test real cross-owner/parent/connection reuse.
3. Complete lifecycle gates around the now immutable originals/profiles and
   metering/settlement facts: sealed build content/manifests, authorized inserts,
   controlled GC and attempt/generation fencing.
   CHECK/FK existence is not cross-table readiness or an immutability trigger.
4. Approve a single migration execution and recovery entry point, and rehearse
   transactions, faults, rollback/recovery and query plans in that isolated target.
5. Validate pg-boss same-connection transactions, quota transitions, source/manifest
   lifecycle and website settlement separately; do not infer them from this DDL.

R1 and R3–R6 are not unlocked. The partial R2 approval permits only this marked
local cluster, synthetic fixtures and its recovery rehearsal. Any other target,
business database, cloud migration or real model requires separate approval.
