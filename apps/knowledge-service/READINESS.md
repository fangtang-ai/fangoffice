## 1. 当前结论

当前交付是已经验证若干底层能力的代码库，不是可供用户操作的云端知识库。云端服务、真实模型、业务流水线、桌面入口没有形成一条已验收链路。测试条数和原任务完成数量均不代表产品可用率。

主要问题是推进和验收单位选错了：围绕底层协议不断补切片，却没有把云端部署、模型调用、用户初始化、业务组装和桌面入口作为同一条交付主线。不是只缺一个地址或密钥，也不是需要先把全部首发任务做完。先交一份 TXT 的纵向闭环，完整首发能力随后推进。

2026-10-21 的核对只涉及 Office 源码、本地配置、原方案和网站 `feat/cloud-knowledge-base` 工作区，没有云端执行；2026-10-22 已按顶部范围完成获准主机、专用试点 PG 及新建知识 OSS 的基础验证，并准备用户指定源的嵌入配置，但未调用真实模型或借用业务/资金数据。旧控制面快照不等于当前资源就绪，基础探针也不等于完整产品验收。

## 3. 把模型的三件事分开

### 3.1 模型服务调用

真实请求 Embedding 供应商，拿回向量和可追踪 usage，属于尚未接入的能力。聊天模型配置和已有聊天 API 通了，不能证明 Embedding 通了。模型密钥只在服务端，不能让桌面自行调模型或决定用户归属。

原方案的验证基线已经是中国内地百炼 `text-embedding-v4`、1024 维、余弦；本地向量表也已经固定 `vector(1024)`。不重新随意选型，也不悄悄更改维度。原方案已记录该模型的 1024 维及 `document`/`query` 语义；实际地域、工作空间、接口类型、密钥权限和可用模型仍须小额真实探针确认。本轮 Context7 查询无命中、web 未返回可读正文，不把历史核验写成这次又核验通过。原生与兼容接口不能混套参数或沿用未经核实的旧聊天地址。

官方接口依据：`https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api`。此处不锁定或沿用旧价格、批量限制和服务地址；接入时按目标地域/工作空间核验。

网站公共政策库已存在 `SemanticEmbeddingService.embedMany`，源码默认模型为 `text-embedding-3-large`、请求维度固定 2048；这是另一套业务索引，不是私有知识库的实际部署模型证明。可参考其批处理/超时处理，不直接复用其索引或搬入整个网站运行时。该方法对外只返回向量数组，不能原样替代私有知识库需要的 profile、用途和 usage 协议。

推荐首个试点由知识服务直接对接百炼原生 HTTP，先不新增 SDK、不先改造聊天网关；这是待审核的实现路径，不是已接通的事实。若必须走现有网关，先证明它正确支持选定模型的维度、文档/查询用途和 usage，再决定复用。适配器至少校验返回条数/顺序、1024 维、有限数和有效向量，保存供应商请求标识；超时后成本不明要记未知，不能记为零或无限重试。

### 3.2 向量空间与检索

模型名、revision、地域、维度、距离、归一化、document/query 用法和切块版本由同一不可变 profile 绑定。资料向量与查询向量必须来自匹配的 profile；不能把网站 2048 维公共索引混入 Office 1024 维私人索引。只建好向量表，不会自动产生向量或检索接口。

### 3.3 模型成本与客户收费

`runtime/embedding.ts`目前记录调用意图、结果、未知成本及更正，没有供应商网络调用。供应商账单、平台 attempt 成本、用户知识余额是三层不同事实。

真实账号初始化、权益/profile、有效预算/回执也是入库前置。当前建空间 SQL 会拒绝没有知识 quota 或 policy 的 owner，队列构建解析会拒绝缺失回执；因此仅补 worker handler 仍不足以跑通。

内部测试可以申请平台承担成本、暂不向客户收费，但必须先明确并实现可审计的试点额度/准入授权；这不是已获批准的旁路，不能插入伪回执、关闭门禁或借用 AI/MCP 余额。若沿原收费链路，需要 C1/C2/C5/C6、D3/D4 的必要接缝；充值商城、礼包和完整运营界面不应成为最小试点的展示前置。

## 4. 责任边界

- 桌面：主动选文件、进度/错误/检索/来源交互；复用登录，不持服务端模型或云管理密钥。
- 同源网关：将账号 API 所在源的 `/api/knowledge` 转发到独立知识 API；独立进程不意味着客户端可直接跨源访问。
- 知识 API：身份、额度、固定对象授权、完成上传短事务、查询/原文读取；不承担长时间解析或模型调用事务。
- 私有 OSS：原文与派生产物；实际禁用版本化、私有策略和最小权限单独验收。
- 知识 PG/pg-boss：owner、profile、版本/build、片段/向量/映射、任务与计量事实；不是第二套钱包。
- 独立 worker：读取原文、解析/切块、真实 Embedding、写入完整产物、封存与原子发布；外部 I/O 不跨持锁事务。
- 网站商业控制面：知识权益/预算/结算权威；不是把整个知识服务嵌进网站后端的理由。
- 写作生成模型：拿检索到的授权证据组织答案，独立于 Embedding；首个检索验收无需先完成双编辑器引用体系。

这里的顺序是依赖顺序，不是必须等第六项完成才能开始写页面：第 4 项接通后即可先交“上传管理可测”，同时继续完成入库/检索所需代码。若任务暂时排队等模型或授权，必须明示阻塞原因，不能显示 ready。真正的知识库功能可测仍要求第 5—7 项通过。

### 5.2 第一次人工验收只测这条路径

1. 用户用明确的测试账号登录，主动选择一份非敏感 TXT；内容包含可核对的名称、日期或金额。
2. 在真实桌面入口上传，看到文件列表、排队/处理中/成功或失败原因；重开应用还能查询同一记录。
3. 直接提问和换一种说法提问，都从真实入库片段返回相符事实，并可点开文件/原文位置核对。
4. 删除资料后发起新查询不再命中；换另一账号不能读取该资料或其来源。
5. 核对这次操作的真实模型请求、Token/未知用量、任务和活动版本证据；无真实向量或失败的文件不能标成功。

这条路径通过才请用户验收“知识库功能”；健康检查、模型探针、上传管理各自单独报告通过，不互相冒名。
